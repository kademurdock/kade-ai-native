# Audio startup and VoiceOver

The owner reported VoiceOver becoming quieter on opening the app and louder during character autoplay, while wanting ordinary VoiceOver ducking preserved. The reviewed native baseline is build 325 source `9c8e2e82f382addd4631c2ab9fded8574ab9a053`. This is a SwiftUI app; there is no Flutter audio-session package in this checkout.

Launch called `Earcons.prewarm`, which created bundled `AVAudioPlayer` instances and called `prepareToPlay` without choosing an audio-session category first. Apple documents that [prepareToPlay activates the audio session](https://developer.apple.com/documentation/avfaudio/avaudioplayer/preparetoplay()) and that the default [soloAmbient category is nonmixing](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/soloambient). Actual buffered and streamed character playback already selects `playback`, `default` mode and `mixWithOthers`. That establishes a source-level launch/playback configuration change consistent with the report; its effect on this phone's VoiceOver volume has not been measured.

Earcon prewarming now caches synthesized WAVs and bundled bytes only. Players and audio hardware are prepared when a feedback sound is actually requested, through the existing deferred main-actor playback path. Before feedback playback, the app selects `ambient` only if the shared session still has its untouched `soloAmbient` category. Apple documents that [ambient mixes with other audio and respects the Silent switch](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/ambient). Other categories, modes and routes belong to the existing recording, duplex call, Clubhouse, reading and character-speech services. Feedback does not activate or deactivate their sessions or change volume levels. If the first mixing configuration fails, that feedback sound is skipped.

The app adds neither `duckOthers` nor `interruptSpokenAudioAndMixWithOthers`. It makes no VoiceOver settings change. [Apple's VoiceOver audio-ducking setting](https://support.apple.com/guide/iphone/change-your-voiceover-settings-iphfa3d32c50/ios) reduces other media and call audio while VoiceOver speaks; that user-controlled behavior remains available. The existing haptics-only warmup and accessibility-audit skip gate remain intact.

`python dev/test_audio_startup.py` checks five source contracts: launch data-only warmup, default-category-only mixing, all feedback entry points before player preparation, preserved playback levels and other audio owners, and the haptics/audit gates. `--baseline` checks the pinned build-325 source to demonstrate the regression; that Git revision must be present locally. These are source checks, not Swift compilation or an acoustic test.

During source-only development, no iPhone, simulator, native build, paid audio job or voice upload was used. Subsequent release verification is recorded separately. The first actual sound now pays the hardware preparation cost; a phone check must confirm its responsiveness as well as launch/idle VoiceOver volume, autoplay start/pause/stop, return from recording or a call, Clubhouse join/leave, and speaker/headphone/Bluetooth behavior. A quiet idle launch and normal VoiceOver ducking need physical confirmation before claiming the reported behavior is fixed.
